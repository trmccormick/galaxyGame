## Purpose and boundaries

The Geosphere owns `terrain_map`, the persisted terrain/geographic dataset associated with a celestial body. This data provides an initial surface representation for mapping, inspection, and surface-view consumers. It is part of the existing sphere architecture; it is not a separate planetary model and does not replace the Geosphere's geological composition, layered mass, materials, tectonic properties, or stored volatile reservoirs.

Keep three responsibilities distinct:

- **StarSim / automatic terrain generation:** creates an initial terrain dataset when a newly created body qualifies and does not already have populated terrain.
- **Map Studio:** the established Admin capability for preparing, generating, reconstructing, and inspecting initial terrain/geographic data. It is not the ongoing environmental simulator.
- **TerraSim:** evolves environmental state and calculates consequences of natural processes, events, and interventions. It should consume the body's modeled state; it is not responsible for creating the initial map.

The Admin Celestial Body View and Surface View may inspect or present the stored data. A presentation adapter does not become the authoritative terrain generator or owner of the map.

See [Celestial Body & Sphere Data Model](celestial_body_and_sphere_data_model.md), [Celestial-Body Sphere Models & Environmental Interactions](sphere_models_and_interactions.md), [TerraSim](terrasim.md), and [Admin Celestial Body View](../ui/05_admin_celestial_body_view.md).

## 1. Existing generation and persistence path

During system construction, `StarSim::SystemBuilderService#generate_automatic_terrain` calls `StarSim::AutomaticTerrainGenerator#generate_terrain_for_body`. The builder wraps generation in error handling and logs a warning if generation fails; it does not make terrain generation a prerequisite for creating the body.

The generator:

1. Checks whether `geosphere.terrain_map` already contains populated terrain data. It accepts a populated hash containing elevation, grid, or biome data, and also recognizes the legacy two-dimensional-array format. Existing populated terrain is not regenerated by this path.
2. Checks whether the body qualifies. The current criteria include terrestrial planets, super-Earths, carbon planets, selected major moons (including Luna, Titan, Ganymede, Callisto, Io, and Europa), sufficiently massive moon instances, and test-named bodies.
3. Selects a source/generation path.
4. Persists the resulting dataset through `store_generated_terrain` to `geosphere.terrain_map`.

The stored map includes the available grid, elevation, biome data, resource grid, strategic markers, resource counts, dimensions, generation method/date, source, quality score and assessment, body properties used for assessment, and generation metadata. Some fields may be empty or absent depending on the generation path; the schema is a common container, not a guarantee that every generator supplies every layer.

## 2. Source selection and generation

For the recognized Sol-world names (Earth, Mars, Luna/Moon, Venus, Mercury, and Titan), the current generator uses this order:

1. **NASA elevation data when a matching source file is found.** The active loader accepts compressed ESRI ASCII grids (`.asc.gz`) and GeoTIFF files. It reads elevation, downsamples it to dimensions calculated from body diameter, and attempts hybrid biome generation.
2. **Body-specific generation** for Earth, Mars, Venus, Mercury, and Luna when the NASA path does not return data.
3. **Generic Civ4/FreeCiv map-based generation** for other recognized Sol bodies or when a body-specific path does not produce data.
4. **AI-assisted procedural generation** as the final fallback.

For bodies outside that Sol-name list, the generator analyzes body properties and calls `AIManager::PlanetaryMapGenerator` with source maps and generation options. Inputs include body radius, terrain complexity, elevation scale, water coverage, temperature, and target grid dimensions. The generated result is transformed into the common stored format.

The code's use of FreeCiv/Civ4 should be described precisely: these maps can supply patterns or geographic guidance in fallback generation paths; they are not equivalent to authoritative measured planetary elevation. NASA elevation data, when present and successfully loaded, has a different evidentiary role from game-map patterns and procedural estimates.

### EarthMapProcessor is a separate import path

`Import::EarthMapProcessor` imports FreeCiv Earth terrain/water structure and Civ4-derived elevation and biome-potential data, with fallback elevation when Civ4 data is unavailable. The inspected `Import::MapLayerService#generate_earth_layers` calls this processor and converts its result into lithosphere, hydrosphere, and biosphere layer data.

This is distinct from the active `AutomaticTerrainGenerator#generate_earth_terrain` path, which tries NASA elevation data and otherwise falls back to the general AI/procedural generator. Although `AutomaticTerrainGenerator` defines an `earth_processor` accessor, the inspected Earth generation method does not call it. Do not assume the MapLayerService/EarthMapProcessor output is what gets persisted to `geosphere.terrain_map`; that connection was not established by this inspection.

### Map Studio's explicit generate/apply workflow

The existing `Admin::MapStudioController` provides a separate, user-directed path:

1. The generation page selects a target celestial body and available source maps.
2. `generate_map` processes selected FreeCiv/Civ4 files and calls `AIManager::PlanetaryMapGenerator#generate_planetary_map`.
3. `save_generated_map` writes a reusable JSON artifact under `GalaxyGame::Paths::GENERATED_MAPS_PATH`, including target-body and source-map metadata.
4. Browse/analyze actions inspect those artifacts.
5. `apply_map` is a separate action. It reads the selected artifact and calls `apply_map_to_celestial_body`, which writes the terrain grid, width, height, and biome counts to `geosphere.terrain_map`. It records the artifact metadata in `celestial_body.properties['applied_map']` and sets `map_source` to `ai_generated`.

This confirms that Map Studio can explicitly update the Geosphere's persisted initial terrain. The saved artifact and the body's applied terrain are separate records/states: generating a map does not by itself apply it to a body.

**Important implementation detail:** the apply method assigns a new `terrain_map` hash containing `grid`, `width`, `height`, and `biome_counts`; it does not merge those fields into the previous terrain hash. The artifact's metadata is stored on `CelestialBody.properties`, not copied into the new `terrain_map` payload by this method. Whether replacing a richer automatically generated terrain map is the intended apply behavior, and whether source/provenance metadata should also be represented with the applied terrain, remain verification/design questions.

The current Map Studio controller flow and its broader limitations are also recorded in [Admin Dashboard and AI Manager](../ui/03_admin_and_ai_manager.md).

## 3. Stored terrain versus surface-view payload

The current Admin Surface action reads `@celestial_body.geosphere&.terrain_map` and passes it to `TerrainDataBuilder#build`.

`TerrainDataBuilder` is a presentation/data-assembly adapter, not a terrain-generation service. It extracts elevation (falling back to the stored grid), biome data, resource grid, dimensions, quality score, and generation method. It also builds a `unit_grid` from craft and locations associated with the body.

One implementation detail to keep distinct from the persisted terrain dimensions: the inspected `extract_unit_grid` currently initializes a fixed 100 × 100 unit grid rather than deriving its dimensions from the terrain map. This is a presentation-coordinate concern to verify when reviewing the Surface View; it does not change the dimensions or contents of `geosphere.terrain_map`.

The existing [Titan elevation data page](titan_elevation_data_generation.md) records Titan-specific source files, conversion history, runtime rendering evidence, and unresolved source/consumer provenance. That history should remain separate from the generic generation contract.

## 4. Relationship to Geosphere and TerraSim

The terrain map is one part of Geosphere state. It should not be confused with:

- crust, mantle, or core composition and mass;
- geological material inventories and deposits;
- stored volatile reservoirs;
- geological/tectonic activity and plate information;
- TerraSim's evolving environmental state.

The map is an initial geographic/surface representation. TerraSim may later alter environmental conditions and, where implemented and required, surface-related state. Do not assume that every environmental change automatically regenerates the terrain map, or that the map is already a time-varying geological elevation simulation. Such coupling must be established from the relevant process and persistence code.

Map Studio's initial-data role and TerraSim's ongoing-evolution role are complementary, not competing systems. The stored map is also not itself a resource ledger: resource grids or markers used for mapping must not be treated as authoritative geological mass inventories unless a separate, verified deposit/material record represents that inventory.

## 5. Implementation findings and open verification

### Confirmed in the inspected code

- The automatic generation entry point is called from StarSim's system-building path.
- Populated terrain data is stored on the body's Geosphere as `terrain_map`.
- Existing populated terrain is skipped by the automatic generator.
- The generator supports NASA elevation loading, body-specific paths, generic map-based fallback, and AI/procedural fallback.
- The persistence payload includes source and generation metadata alongside terrain layers and quality information.
- The Admin Surface action consumes the stored map through `TerrainDataBuilder`.
- `EarthMapProcessor` is used by `MapLayerService#generate_earth_layers`, a distinct layer-import path.

### Questions to retain for future code review

1. Confirm the intended semantics when Map Studio applies a generated map over an existing, potentially richer `terrain_map`; the current controller replaces the hash with a smaller grid/dimensions/biome-count payload.
2. Trace each consumer of `terrain_map` and distinguish the persisted map, generated layer payloads, and surface-rendering payloads.
3. Verify which source files are actually present and selected for each Sol body in the active runtime. The existence of a lookup method or historical task note is not proof that a file is available in every environment.
4. Review the fixed 100 × 100 unit-grid dimensions against actual terrain-map dimensions and the Surface View coordinate contract.
5. Verify the resource-grid/strategic-marker behavior per generation path. The inspected NASA helper methods currently return empty placeholders for resource grids, markers, and counts; other paths may supply different data.
6. Continue the existing Titan provenance investigation before renaming, deleting, or consolidating any retained source or intermediate elevation products.

These are focused provenance, consumer, and presentation checks around an existing generation/storage architecture. They are not instructions to rebuild the Geosphere or create another terrain model.
